The Pretraining Loop and Compute Accounting

What must work before a small Transformer becomes a language model?

The idea

A pretraining run needs a consistent tokenizer, causal objective, data pipeline and verified training loop. Track validation loss alongside token count, model size and compute. Begin with a small checkable run before treating resource scale as the main problem.

Compute estimates help compare experiments but are not runtime predictions. Architecture, sequence length, recomputation and hardware efficiency all affect actual cost. Checkpointing should restore not only weights but the state required to continue the same optimisation process.

Read the relationship

Rough dense-training estimate: FLOPs≈6ND

N denotes model parameters and D training tokens in this convention. The constant is a common coarse accounting rule, not an exact hardware benchmark.

Work through an example

  1. For N=10⁸ parameters and D=10⁹ tokens, the estimate gives 6×10¹⁷ floating-point operations.
  2. Changing context length or architecture can add costs not captured accurately by that simple estimate.
  3. Verify gradient accumulation and update counts on a tiny run before paying for a larger one.

When it applies

A successful toy run establishes only that scale and setup. It is not evidence of reproducing a frontier model or its capabilities.

Check your understanding

If four microbatches accumulate into one update, what must loss scaling preserve?

The intended effective-batch gradient; otherwise accumulating gradients silently changes the optimisation objective or step size.
