Tokenisation, Embeddings and Position

How does text become a sequence of vectors?

The idea

A tokenizer converts text into discrete token IDs. An embedding table maps each ID to a learned vector. Tokens may be words, subwords, bytes or other units; they are not a universal character count, and the same visible string can be split differently by different tokenizers.

Position information tells a sequence model about order. Vocabulary, special tokens, context length and position conventions all affect the actual input. These choices must stay consistent between training and inference; an embedding vector alone does not intrinsically encode where it appeared.

Read the relationship

IDs∈{0,…,V−1}^(B×T); embedding table E∈R^(V×d)

V is vocabulary size, B batch size, T sequence length and d embedding width. Indexing the table produces a B×T×d tensor.

Work through an example

  1. With a vocabulary of 32,000 and width 512, the table holds 32,000×512=16,384,000 parameters.
  2. That count does not multiply by the number of tokens in a particular prompt.
  3. If input and output embeddings share weights, the storage and parameter accounting must reflect that sharing.

When it applies

Vocabulary size and token length depend on the tokenizer and language. Character counts are not exact token estimates.

Check your understanding

Is one token always one English word?

No. A word can split into several tokens, and a token can represent other kinds of text fragment.
