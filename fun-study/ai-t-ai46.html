Robustness, Safety and Use Boundaries

Which changes or failures does a system need to withstand?

The idea

Robustness is always relative to a specified set of changes. Natural distribution shift, adversarial perturbations, privacy leakage, biased outcomes and unauthorised tool actions are different problems. Define who can change what, what they seek and which outcomes count as failures.

Tests should match the application rather than becoming a generic checklist. Red-team discoveries demonstrate concrete failure modes; passing a finite collection of tests is not a universal mathematical guarantee. Limit authority and make consequential actions observable and recoverable where possible.

Read the relationship

Threat model=(actor, allowed changes, objective, failure criterion)

The permitted attacker or environment changes determine the claim being tested. A robustness statement without a threat model is underspecified.

Work through an example

  1. Place an instruction-like sentence inside a retrieved document, such as a demand to ignore the task.
  2. Treat it as untrusted document content and test whether it improperly changes tool actions.
  3. Run this check in a restricted setting and inspect the resulting actions, not only the final prose.

When it applies

One successful refusal or one passed perturbation does not establish safety across all contexts. Privacy, fairness and control guarantees require different evidence.

Check your understanding

Why is least privilege useful even when a model is usually reliable?

It limits the consequences of the failures that testing and confidence cannot completely exclude.
